## 프롤로그: 하나의 질문에서 시작하겠습니다

> "DB 커넥션이랑 애플리케이션 커넥션은 다른 건가요?"

이 질문을 받았을 때, 대부분의 개발자는 JDBC, HikariCP, 트랜잭션 같은 키워드를 떠올립니다. 하지만 이 질문에 제대로 답하려면, 먼저 더 근본적인 질문을 해야 합니다.

> "커넥션을 맺는다는 건, 도대체 어떤 행위를 하는 건가요?"

이 글은 이 질문에서 출발합니다. DB도, 애플리케이션도 잠시 잊으세요. 우리가 먼저 이해해야 할 것은 운영체제의 세계입니다. 커넥션이라는 단어는 DB의 전유물이 아닙니다. OS가 먼저 만들고, 프로토콜이 의미를 부여하고, 애플리케이션이 빌려 쓰는 것입니다.

---

## 1. "커넥션을 맺는다"는 것

### 1.1 운영체제의 관점에서

커넥션이라는 단어를 들으면, 두 시스템이 서로 연결된 상태를 떠올립니다. 맞습니다. 하지만 운영체제 입장에서 "커넥션을 맺는다"는 것은 매우 구체적인 행위입니다. 그것은 커널이 **소켓(socket)**이라는 자료구조를 생성하고, 상대방의 소켓과 양방향 바이트 스트림을 주고받을 수 있는 상태로 만드는 것입니다.

여기서 핵심은 **"상태"**라는 단어입니다. 커넥션은 물리적 전선이 아닙니다. 커널 메모리 안에 존재하는 상태(state)입니다. 두 호스트의 커널이 각각 "나는 상대방과 연결되어 있다"는 상태를 유지하고 있을 때, 우리는 커넥션이 맺어졌다고 말합니다.

```c
// 리눅스 커널의 소켓 생성
int fd = socket(AF_INET, SOCK_STREAM, 0);  // TCP 소켓 생성
connect(fd, &server_addr, sizeof(server_addr));  // 연결 시도
```

이 두 줄의 시스템 콜이 수행되면, 커널은 파일 디스크립터 테이블에 새 엔트리를 만들고, 그 엔트리가 소켓 구조체를 가리키게 합니다. `connect()`가 성공하면 이 소켓의 상태가 `ESTABLISHED`로 전이됩니다. 이것이 커넥션의 실체입니다. 디스크에 뭔가를 쓰는 것도 아니고, 전선을 꽂는 것도 아닙니다. **커널 메모리에 상태를 기록하는 것**입니다.

### 1.2 그러면 커넥션 없이는 통신이 불가능한가?

> "커넥션을 맺어야만 핸드셰이크도 하고 통신이 가능해지는 건가요?"

순서가 중요합니다. 정확히는 이렇습니다: **핸드셰이크를 해야 커넥션이 맺어지는 것**이지, 커넥션이 맺어진 후에 핸드셰이크를 하는 것이 아닙니다.

TCP의 3-Way Handshake(`SYN → SYN-ACK → ACK`)는 커넥션을 맺는 과정 그 자체입니다. 이 세 패킷의 교환이 성공하면, 양쪽 커널이 각각 소켓의 상태를 `ESTABLISHED`로 바꿉니다. 이 시점에서 비로소 커넥션이 존재하게 됩니다.

그리고 TCP 없이도 통신은 가능합니다. UDP는 커넥션 없이 패킷을 보냅니다. 상대방이 받았는지, 순서가 맞는지, 빠진 것은 없는지 보장하지 않지만 통신 자체는 됩니다. DNS 쿼리가 대표적입니다. 커넥션이라는 개념은 "신뢰할 수 있는 양방향 통신"을 위한 약속이지, 통신의 전제 조건이 아닙니다.

> 💡 **커넥션 = 커널 메모리에 존재하는 상태.** 물리적 전선이 아니라, 양쪽 OS가 합의한 "우리는 지금 연결되어 있다"는 약속입니다.

## 2. 물리적 연결과 논리적 연결: 종이컵 전화기와 유선전화

### 2.1 비유를 통한 구분

물리적 연결과 논리적 연결의 차이를 이해하기 위해, 아주 오래된 장난감을 떠올려봅시다.

**종이컵 전화기**를 생각해보세요. 두 개의 종이컵을 실로 연결합니다. 실이 팽팽하게 당겨져 있어야 소리가 전달됩니다. 실이 끊어지면 통신이 끊깁니다. 이것이 **물리적 연결**입니다. 연결의 매개체가 눈에 보이고, 손으로 만질 수 있고, 끊어지면 물리적으로 복구해야 합니다.

이제 **유선전화**를 생각해보세요. 벽에 전화선을 꽂으면, 전화국의 교환기를 거쳐 상대방과 연결됩니다. 여기서 중요한 점은, 전화기를 내려놓아도 전화선은 여전히 벽에 꽂혀 있다는 것입니다. 물리적 선은 항상 연결되어 있지만, "통화"라는 **논리적 연결**은 수화기를 들고 번호를 눌러야 성립하고, 수화기를 내리면 끊어집니다.

### 2.2 네트워크에서의 대응

이 비유를 네트워크로 가져오면 이렇게 됩니다.

| 구분 | 물리적 연결 | 논리적 연결 |
|---|---|---|
| **비유** | 종이컵 + 실 | 유선전화 통화 |
| **네트워크** | 이더넷 케이블, 광섬유, NIC | TCP 소켓 (커널의 상태) |
| **끊어지면?** | 랜선을 다시 꽂아야 함 | 커널이 상태를 다시 만들면 됨 |
| **존재 조건** | 물질이 연결되어 있어야 함 | 양쪽 OS의 합의만 있으면 됨 |

개발자가 코드에서 다루는 커넥션은 전부 논리적 연결입니다. `DriverManager.getConnection()`이 반환하는 것은 랜선이 아닙니다. 커널의 소켓 상태 위에 DB 프로토콜이 한 겹 더 얹어진 논리적 구조물입니다. 물리적 연결(케이블, NIC, 스위치)은 이미 인프라 레벨에서 완성되어 있고, 그 위에서 논리적 연결을 맺었다 끊었다 하는 것이 우리가 말하는 "커넥션"입니다.

> 💡 **물리적 연결 = 케이블이 꽂혀 있는 상태. 논리적 연결 = 그 케이블 위에서 OS가 만든 소켓 상태.** 개발자가 다루는 모든 커넥션은 논리적 연결입니다.

## 3. 그렇다면 DB 커넥션이란 무엇인가

### 3.1 논리적 연결 위에 쌓이는 또 다른 논리적 연결

여기서 이야기가 한 단계 더 깊어집니다. TCP 커넥션이 맺어졌다고 해서, DB 커넥션이 자동으로 만들어지는 것이 아닙니다.

TCP 커넥션은 "양쪽 커널이 바이트 스트림을 주고받을 준비가 되었다"는 상태일 뿐입니다. 이 파이프 위에 MySQL 프로토콜이 올라갈 수도 있고, HTTP가 올라갈 수도 있고, 자체 프로토콜이 올라갈 수도 있습니다. 커널은 관심이 없습니다.

DB 커넥션이 되려면, TCP 커넥션이 수립된 후에 **DB 고유의 프로토콜 핸드셰이크**가 추가로 필요합니다. MySQL을 예로 들면, 서버가 먼저 자신의 버전과 인증 정보를 담은 패킷을 보내고, 클라이언트가 사용자 이름과 비밀번호로 응답하고, 서버가 인증을 확인한 후 OK를 보냅니다. 이 과정이 끝나야 비로소 DB 세션이라는 것이 탄생합니다.

즉, 커넥션에는 계층이 있습니다.

| 계층 | 무엇이 하는가 | 만들어지는 것 |
|---|---|---|
| **L1~L2** | 케이블, NIC, 스위치 | 물리적 연결 (전기 신호가 오갈 수 있는 상태) |
| **L4** | 커널 (TCP 스택) | TCP 커넥션 (소켓 상태 = 1차 논리적 연결) |
| **L7** | DB 서버 프로세스 | DB 세션 (인증 + 상태 컨테이너 = 2차 논리적 연결) |
| **App** | JDBC 드라이버 / 커넥션 풀 | Connection 객체 (위 모든 것을 캡슐화한 래퍼) |

개발자가 "DB 커넥션"이라고 부르는 것은 이 모든 계층이 한 번에 수립된 결과물입니다. 하나처럼 보이지만 실제로는 네 겹의 합작품입니다.

### 3.2 DB 세션이 짊어지는 무게

TCP 커넥션 위에 DB 세션이 만들어지면, 그 세션은 상태를 갖기 시작합니다. 트랜잭션의 격리 수준, `SET`으로 바꾼 세션 변수, 임시 테이블, Prepared Statement 캐시, 현재 진행 중인 트랜잭션의 락 정보까지. 이 상태가 세션이 끊어질 때 전부 사라집니다.

그렇기 때문에 DB 커넥션을 새로 만드는 것은 단순히 TCP 소켓을 여는 것보다 훨씬 비쌉니다. TCP 핸드셰이크에 이어, DB 프로토콜 핸드셰이크, 인증, 그리고 세션 초기화까지 수행해야 합니다. 동일 데이터센터 내에서도 이 전체 과정에 수 밀리초가 걸리고, 리전 간이라면 수백 밀리초가 걸립니다.

> 💡 **커넥션의 수립 비용:** TCP Handshake (~0.5ms) + TLS Handshake (~1-2ms) + DB 인증 및 세션 초기화 (~1-5ms) = 동일 DC 내에서도 약 3~8ms. 단순 SELECT 쿼리(~0.1ms)보다 수십 배 비쌉니다.

## 4. 커넥션 풀이 진짜로 들고 있는 것

### 4.1 핵심 질문

이제 이 글의 핵심 질문으로 돌아옵시다.

> "Spring에서 DB 커넥션 풀을 만들면, 트랜잭션을 사용하지 않아도 유휴 커넥션들이 있잖아요. 이 커넥션들은 물리적으로 연결되어 있는 건가요?"

이 질문을 제대로 이해하려면, 앞에서 정리한 계층 구분이 필수입니다.

### 4.2 답: 유휴 커넥션은 논리적으로 연결되어 있다

**물리적 연결(케이블, NIC)의 관점에서 보면**, 그것은 커넥션 풀과 무관하게 항상 연결되어 있습니다. 서버가 데이터센터에 있고 랜선이 꽂혀 있으면, 애플리케이션이 기동 중이든 종료되었든 물리적 연결은 존재합니다. 이 레이어는 커넥션 풀의 관심사가 아닙니다.

**TCP 소켓의 관점에서 보면**, 유휴 커넥션은 실제로 `ESTABLISHED` 상태의 TCP 소켓을 유지하고 있습니다. 커널 메모리에 소켓 구조체가 존재하고, 파일 디스크립터가 할당되어 있고, 상대방 DB 서버의 커널에도 대응하는 소켓이 존재합니다. 아무 데이터도 오가지 않지만, 양쪽 커널 모두 "이 연결은 살아있다"는 상태를 유지합니다.

**DB 세션의 관점에서 보면**, DB 서버에도 해당 커넥션에 대응하는 세션(또는 스레드, 또는 프로세스)이 존재합니다. MySQL이라면 `SHOW PROCESSLIST`에서 `Sleep` 상태로 보이고, PostgreSQL이라면 `pg_stat_activity`에서 `idle` 상태로 보입니다.

```sql
mysql> SHOW PROCESSLIST;
+----+------+-----------+------+---------+------+-------+------------------+
| Id | User | Host      | db   | Command | Time | State | Info             |
+----+------+-----------+------+---------+------+-------+------------------+
| 42 | app  | 10.0.1.5  | mydb | Sleep   | 127  |       | NULL             |
| 43 | app  | 10.0.1.5  | mydb | Sleep   | 84   |       | NULL             |
| 44 | app  | 10.0.1.5  | mydb | Query   | 0    | exec  | SELECT * FROM... |
+----+------+-----------+------+---------+------+-------+------------------+
```

Id 42와 43이 유휴 커넥션입니다. 아무 쿼리도 실행하지 않지만, TCP 소켓도 살아있고 DB 세션도 살아있습니다. 커널의 소켓 버퍼가 메모리를 먹고 있고, DB 서버의 스레드(또는 프로세스)가 자원을 점유하고 있습니다. **놀고 있지만 비용은 지불하고 있는 상태**입니다.

> 💡 유휴 커넥션은 "연결이 끊어진 상태"가 아닙니다. TCP 소켓도 `ESTABLISHED`이고, DB 세션도 `idle` 상태로 살아있습니다. 단지 아무 데이터도 흐르지 않을 뿐입니다. 비유하자면, 유선전화의 수화기를 들고 있지만 아무 말도 안 하는 상태입니다.

### 4.3 그러면 왜 굳이 연결을 유지하는가

> "연결이 안 되어 있다면 커넥션 풀의 존재 이유가 뭔가요?"

바로 이겁니다. 커넥션 풀은 **연결이 안 되어 있는 게 아니라, 연결을 미리 만들어서 유지하고 있는 것**입니다. 그리고 그 이유는 커넥션 수립 비용이 비싸기 때문입니다.

만약 매 요청마다 커넥션을 새로 만든다면, 앞서 본 것처럼 3~8ms(혹은 그 이상)의 수립 비용을 매번 지불해야 합니다. 초당 1,000건의 요청을 처리하는 서버라면, 순수하게 커넥션 수립에만 초당 3~8초가 소비되는 셈입니다. 이것은 산술적으로 불가능한 숫자입니다.

커넥션 풀은 이 비용을 한 번만 지불하고, 이후에는 이미 수립된 커넥션을 재사용합니다. 풀에서 커넥션을 꺼내는 비용은 수 마이크로초에 불과합니다. **수 밀리초 대 수 마이크로초, 약 1,000배의 차이입니다.**

| 방식 | 커넥션 획득 비용 | 초당 1,000 요청 시 |
|---|---|---|
| **매번 새로 생성** | ~3-8ms | ~3-8초 (불가능) |
| **커넥션 풀에서 대여** | ~0.003-0.01ms | ~3-10ms (무시 가능) |

커넥션 풀의 존재 이유는 "연결을 미리 만들어서 유지하는 비용"이 "매번 새로 만드는 비용"보다 압도적으로 싸기 때문입니다. 유휴 커넥션이 TCP 소켓과 DB 세션을 유지하면서 자원을 소비하는 것은 사실이지만, 그 비용은 매 요청마다 커넥션을 수립하고 해제하는 비용에 비하면 미미합니다.

## 5. 유휴 커넥션이 "살아있다"의 함정

### 5.1 커널은 알고 있지만, 애플리케이션은 모른다

여기서 실무적으로 중요한 함정이 등장합니다. 커넥션 풀의 유휴 커넥션이 "살아있다"는 것은 **애플리케이션이 그렇게 믿고 있다는 뜻**이지, 실제로 살아있다는 보장은 아닙니다.

유휴 커넥션이 오래 방치되면, 중간 경로의 방화벽, 로드밸런서, 또는 NAT 장비가 일방적으로 TCP 세션을 정리할 수 있습니다. 이 장비들은 일정 시간 동안 패킷이 오가지 않는 커넥션을 죽은 것으로 간주하고 자신의 세션 테이블에서 제거합니다. 이때 양쪽 호스트에게 아무런 통보도 하지 않습니다.

이 상태가 바로 **half-open connection**입니다. 애플리케이션 쪽 커널은 소켓이 `ESTABLISHED`라고 알고 있고, DB 서버 쪽도 마찬가지입니다. 하지만 중간 경로가 끊어져 있으므로, 실제로 패킷을 보내는 순간 비로소 연결이 죽었다는 사실을 알게 됩니다.

```
// 풀에서 꺼낸 커넥션으로 쿼리 실행 시도
// → TCP RST 수신 → "Connection reset by peer"
// → 또는 타임아웃까지 무응답 → "Socket read timed out"
```

### 5.2 커넥션 풀은 어떻게 방어하는가

이 문제에 대한 커넥션 풀의 방어 전략은 크게 세 가지입니다.

**첫째, Validation Query(연결 검증 쿼리)입니다.** 커넥션을 풀에서 꺼낼 때 또는 주기적으로, `SELECT 1` 같은 가벼운 쿼리를 실행해서 커넥션이 살아있는지 확인합니다. 죽어있으면 폐기하고 새 커넥션을 만듭니다.

**둘째, TCP Keepalive입니다.** OS 레벨에서 주기적으로 빈 패킷을 보내서, 중간 장비의 세션 테이블을 갱신하고 연결이 살아있는지 확인합니다. 이것은 커널이 하는 일이지 애플리케이션이 하는 일이 아닙니다.

**셋째, Max Lifetime(최대 수명)입니다.** 커넥션이 아무리 건강해도, 일정 시간이 지나면 강제로 폐기하고 새로 만듭니다. HikariCP의 기본값은 30분입니다. 이것은 "오래된 커넥션은 믿지 않겠다"는 보수적인 전략입니다.

```yaml
# HikariCP 설정
spring.datasource.hikari.connection-test-query=SELECT 1
spring.datasource.hikari.keepalive-time=300000     # 5분
spring.datasource.hikari.max-lifetime=1800000      # 30분
spring.datasource.hikari.minimum-idle=5
spring.datasource.hikari.maximum-pool-size=10
```

> 💡 커넥션 풀의 유휴 커넥션은 "연결되어 있다고 믿는" 상태입니다. 실제로 살아있는지는 패킷을 보내봐야 알 수 있습니다. Validation Query와 TCP Keepalive는 이 간극을 메우기 위한 장치입니다.

## 6. 다시 처음 질문으로: DB 커넥션과 애플리케이션 커넥션

### 6.1 OS는 구분하지 않는다

> "DB 커넥션이랑 애플리케이션 커넥션은 다른 건가요?"

운영체제의 관점에서 답하면: **같습니다.** 정확히는, OS는 그 구분 자체를 하지 않습니다.

커널에게 소켓은 소켓일 뿐입니다. 그 소켓 위로 MySQL 패킷이 흐르든, HTTP 요청이 흐르든, gRPC 호출이 흐르든, 커널이 하는 일은 동일합니다. 바이트를 받아서 TCP 세그먼트로 감싸고, IP 패킷으로 감싸고, 이더넷 프레임으로 감싸서 NIC에 전달하는 것입니다. 역방향도 마찬가지입니다.

```bash
$ ss -tnp
ESTAB  10.0.1.5:48234  10.0.1.10:3306   java    # DB 커넥션
ESTAB  10.0.1.5:48240  10.0.1.20:8080   java    # HTTP 커넥션
ESTAB  10.0.1.5:48250  10.0.1.30:6379   java    # Redis 커넥션
```

`ss` 명령의 출력에서 이 세 줄의 차이는 목적지 IP와 포트 번호뿐입니다. 커널이 이것들을 관리하는 방식, 할당하는 자원, 유지하는 상태는 완전히 동일합니다. "DB 커넥션"과 "애플리케이션 커넥션"은 커널이 아닌, **L7 프로토콜과 개발자의 관점에서만 의미 있는 구분**입니다.

### 6.2 프로토콜이 만드는 차이

그러면 왜 우리는 이것들을 다르게 느끼는 걸까요? 그것은 그 소켓 위에 올라가는 프로토콜이 만드는 차이 때문입니다.

**HTTP 커넥션**은 stateless합니다. 각 요청은 독립적이고, 커넥션 위에 세션 상태가 거의 없습니다. 그래서 HTTP/2에서는 하나의 TCP 커넥션 위에 수백 개의 요청을 동시에 실어 보낼 수 있습니다.

**DB 커넥션**은 stateful합니다. 트랜잭션 상태, 세션 변수, 임시 테이블, Prepared Statement 캐시 등이 세션에 묶여 있습니다. 그래서 커넥션을 다른 클라이언트와 공유하는 것이 구조적으로 어렵습니다.

이 stateful/stateless의 차이가, 같은 TCP 소켓임에도 불구하고 DB 커넥션이 특별한 관리(풀링, 수명 관리, 검증)를 필요로 하는 근본적인 이유입니다.

## 7. 이 이해가 실무에서 의미하는 것

### 7.1 커넥션 풀 사이징

커넥션 풀의 크기를 결정할 때, 많은 개발자가 "크면 클수록 좋다"고 생각합니다. 하지만 유휴 커넥션도 TCP 소켓과 DB 세션을 점유한다는 사실을 이해하면, 이것이 왜 틀린 생각인지 알 수 있습니다.

PostgreSQL은 커넥션 하나가 프로세스 하나입니다. 커넥션이 100개면 프로세스가 100개 떠 있습니다. 유휴 상태라도 프로세스당 5~10MB의 메모리를 소비합니다. MySQL은 커넥션 하나가 스레드 하나이지만, 수천 개의 스레드가 존재하면 컨텍스트 스위칭 비용이 실제 쿼리 처리 시간을 초과할 수 있습니다.

> 💡 **적정 풀 크기 ≈ CPU 코어 수 × 2.** 직관에 반하지만, 작은 풀이 큰 풀보다 처리량이 높은 경우가 많습니다. 커넥션이 늘어나면 락 경합, 메모리 압박, 컨텍스트 스위칭이 모두 증가하기 때문입니다.

### 7.2 장애 분석의 출발점

커넥션의 계층을 이해하면, 장애 분석의 출발점이 달라집니다. "커넥션 에러"가 발생했을 때, 문제가 어느 계층에 있는지를 먼저 파악해야 합니다.

`Connection timed out`이면 TCP 레벨(L4)입니다. 네트워크 경로에 문제가 있거나, 대상 서버의 백로그 큐가 가득 찬 것입니다. `Access denied`나 `Too many connections`이면 DB 프로토콜 레벨(L7)입니다. 인증 실패이거나 DB 서버의 `max_connections`에 도달한 것입니다. `Connection pool exhausted`이면 애플리케이션 레벨입니다. 코드에서 커넥션을 반환하지 않고 있거나, 풀 크기가 부족한 것입니다.

같은 "커넥션 에러"라도 계층에 따라 진단 도구와 해법이 완전히 다릅니다. `tcpdump`로 패킷을 봐야 할 수도 있고, DB 로그를 봐야 할 수도 있고, 스레드 덤프를 떠야 할 수도 있습니다. 커넥션이 무엇인지를 모르면, 어디를 봐야 할지도 모릅니다.

### 7.3 CLOSE_WAIT: 계층 사이에서 벌어지는 일

계층 분리를 체화하면 이해할 수 있는 대표적인 현상이 `CLOSE_WAIT`입니다. DB 서버가 커넥션을 끊었는데(FIN을 보냈는데), 애플리케이션이 `close()`를 호출하지 않으면, 소켓이 `CLOSE_WAIT` 상태에 머뭅니다. 커널은 애플리케이션이 `close()`를 호출하기를 기다리고, 애플리케이션은 커넥션 객체를 참조하고 있지만 사용하지 않습니다. 이 소켓은 타임아웃으로 자동 정리되지 않습니다. 파일 디스크립터를 영구히 점유합니다. 이것이 쌓이면 `Too many open files`로 서버 전체가 멈춥니다.

`CLOSE_WAIT`은 커널(L4)이 보내는 신호를 애플리케이션(L7)이 무시할 때 발생합니다. 물리적 연결과 논리적 연결의 계층이 다르기 때문에 일어나는 현상이며, 이 계층 구분을 모르면 원인을 진단할 수 없습니다.

## 결론: 커넥션을 보는 눈

처음 질문으로 돌아갑시다.

> "DB 커넥션이랑 애플리케이션 커넥션은 다른 건가요?"

OS에게는 같습니다. 둘 다 TCP 소켓이고, 파일 디스크립터이고, 커널 메모리의 상태입니다. 그 위에 어떤 프로토콜이 올라가느냐에 따라 DB 커넥션이 되기도 하고, HTTP 커넥션이 되기도 합니다.

커넥션을 맺는다는 것은 전선을 꽂는 행위가 아닙니다. 양쪽 OS가 "우리는 연결되어 있다"는 상태를 합의하는 것입니다. 커넥션 풀이 유지하는 유휴 커넥션은 물리적으로 연결되어 있냐는 질문에 대한 답은 이것입니다: **물리적 연결(케이블)은 커넥션 풀과 무관하게 항상 존재하고, 논리적 연결(TCP 소켓 + DB 세션)은 유휴 상태에서도 유지되며 자원을 소비합니다.** 커넥션 풀의 존재 이유는 이 논리적 연결의 수립 비용이 비싸기 때문에, 한 번 만들어놓고 재사용하는 것입니다.

이 계층 구분을 체화하면, 커넥션 풀의 설정값이 왜 그런지, 장애가 어디에서 발생한 건지, 그리고 왜 "커넥션"이라는 하나의 단어가 이렇게 많은 혼란을 일으키는지가 명확해집니다. 추상화는 편리하지만, 추상화 아래를 볼 줄 알 때 비로소 도구를 제대로 쓸 수 있습니다.
